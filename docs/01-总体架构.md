# 01 · 总体架构

> **范围原则：功能等价优先。** 关键算法参考原项目源码，但不要求 Unity 2019 数值逐帧一致；
> Unity 2019 数据对拍属于可选精确模式，范围与验收以 [17-功能范围与验收](17-功能范围与验收.md) 为准。

## 2. 对象树（运行时）

与原项目一致的“根→层→状态”树：

```
AnimancerPlayable              (≈ 原 AnimancerPlayable)
 ├─ PlayableGraph              (≈ Unity PlayableGraph，本库自实现)
 │   ├─ ScriptNode(root)       (承载 AnimancerPlayable 的更新回调)
 │   ├─ LayerMixerNode         (≈ AnimationLayerMixerPlayable)
 │   │   ├─ AnimancerLayer[0]  (≈ AnimancerLayer, 内部是 MixerNode)
 │   │   │   ├─ ClipState
 │   │   │   └─ ManualMixerState
 │   │   │        └─ ClipState ...
 │   │   └─ AnimancerLayer[1] ...
 │   └─ PostUpdateNode         (≈ 原 PostUpdate，用于 post-update 列表)
 └─ PlayableOutput -> Skeleton::apply(Pose)
```

说明：
- 原项目把 `AnimancerPlayable` 自身挂成一个 `ScriptPlayable`，并另建一个 `PostUpdate` 脚本节点接在 root 的第 2 个输入口上用于 post-update。本库照搬该结构（见 [06-Playable图](06-Playable图.md)）。
- Layer 内部是一个 `AnimationMixerPlayable`，每个 State 占一个输入口，输入权重=State.Weight。
- `ManualMixerState` 自身也是 `AnimancerState`，其 playable 又是一个 `AnimationMixerPlayable`，形成递归。

## 3. 更新循环（关键！）

原项目依赖 Unity Playables 的 `PrepareFrame` 两次调用实现“双阶段更新”。本库自建等价机制：

```
帧开始
 └─ AnimancerPlayable::evaluate(dt):
     1. 早期更新阶段 (PrepareFrame)：
        预分配 DeltaTime、FrameID
        调用 _PreUpdatables (按逆序)，驱动：
          - 权重淡入淡出 (AnimancerNode::update -> updateFade + applyWeight)
          - IsPlaying 脏标记应用 (AnimancerState::update)
          - 延迟设置 Time (_MustSetTime)
          - 混合器重算权重 (ManualMixerState::update -> recalculateWeights)
       同步更新 PostUpdateNode 的连接状态
     2. 图求值阶段 (ProcessFrame)：
        自底向上，每个节点求值产生 Pose（Clip 采样 / 混合 / Layer 混合）
     3. 后期更新阶段 (PostUpdateNode 的 PrepareFrame)：
        调用 _PostUpdatables，主要是 EventDispatcher（事件触发）
     4. 输出：root 输出 Pose -> Skeleton::apply
```

原项目出处：
- 早期更新：`AnimancerPlayable.cs:1234 PrepareFrame` -> `UpdateAll(_PreUpdatables, ...)`。
- 后期更新：`AnimancerPlayable.cs:1310 PostUpdate` 类，`:1379 PrepareFrame` -> `UpdateAll(_PostUpdatables,...)`。
- 时间脏标记与事件：`AnimancerState.cs:472 TimeD`（`IsRunningPostUpdate` 时延迟到下一次 pre-update）。
- 权重更新：`AnimancerNode.cs:341 Update` / `:713 UpdateFade` / `:560 ApplyWeight`。

> 双阶段的意义（原注释，`AnimancerPlayable.cs:1383`）：post-update 里修改时间可以，但修改权重不行——否则“事件里切换动画”会出现旧动画权重还没归零却已回到第 0 帧的错误。因此时间改动延迟到下一帧 early-update 与权重同步。

### 3.1 执行模型：图求值 vs. 任务调度（重要）

“图求值”与“任务调度”是两个维度，必须分开：

- **图求值**：单个 `AnimancerPlayable` 内部的节点依赖（采样→混合→层→输出）。这是**拉取式**，默认在同一线程内按拓扑序完成。
- **任务调度 / Animation Jobs**：Unity 的 `IAnimationJob` 由 C# Job System 执行；本库用 `IJobScheduler`（见 [16](16-任务调度与ECS集成.md)）执行，默认单线程，可换并行后端。
- **ECS**：EnTT 等只决定“角色/组件/系统如何组织与遍历”，**不提供线程池**。是否使用 EnTT 不影响核心库；详见 [16](16-任务调度与ECS集成.md)。

跨角色可以并行；单角色内部的 IK 链有依赖，需串行。调色板计算与渲染上传之间的同步点由集成层负责（见 [12](12-引擎集成-bgfx.md)）。

## 4. 数据流

```
Clip(.ab) ──sample(t)──▶ [L3 Pose] ──逐层/混合──▶ [L3 Pose]
                                   │
         HumanoidClip ──muscle→local(avatar,T-Pose)──┘
                                   │
                          PlayableOutput
                                   │
                    Skeleton::apply(pose) ──▶ Mat4 调色板 ──▶ bgfx 蒙皮
```

- 普通骨骼 Clip：`sample` 直接得到每骨局部 TRS。
- 人形 Clip：`sample` 得到肌肉值 → `MuscleSpace::toLocal` 用目标 Avatar 转成每骨局部旋转（详见 05）。
- 根运动：在 `Pose` 应用前从 Hips 提取 delta（详见 04/10）。

## 5. 命令系统（防时序错乱）

原项目 Layer 用 `CommandCount` 记录 `CurrentState` 变化次数（`AnimancerLayer.cs:79-99`）。用途：外部缓存当时计数，之后比较即可知道“期间是否又切换过状态”，用于 `CustomFade` 自我取消等（`CustomFade.cs:115,147`）。本库保留该机制。

## 6. 所有权与生命周期

- `AnimancerPlayable` 拥有 `LayerList` 与 `StateDictionary`（原 `AnimancerPlayable.cs:386-387`）。
- State 由 `StateDictionary` 注册/注销（原 `StateDictionary.cs`），析构/`destroy()` 时注销。
- Layer 拥有其子 State 的连接（`AnimancerLayer::addChild/onRemoveChild`，原 `AnimancerLayer.cs:169-215`）。
- Graph 节点由 Graph 统一持有；`destroy()` State/Node 时从父输入口断开。

## 8. 非目标映射说明

- `PlayableAssetState`（Unity Timeline）：本库以 `ScriptNode`（图节点）+ `IAnimationJob`/回调实现等价“在图上插入自定义处理”的能力。
- `ControllerState`（RuntimeAnimatorController 状态）：本库不解析 `.controller`；用 `ClipTransitionSequence` / FSM 组合替代。
- `SoloAnimation`（独立单动画组件）：可作为 `PlayableOutput` 的极简用法保留（已实现，见 15）。
- Unity 的 C# Job System / Burst：以 `IJobScheduler`（默认 `InlineJobScheduler`，可注入 `ThreadPoolJobScheduler`）替代；`Burst` 的 SIMD 热点用 mecanim `xform` 3×float4 + SSE2 实现。EnTT 仅作可选 ECS 适配，详见 [16](16-任务调度与ECS集成.md)。

## 9. 当前状态与性能（P7）

- P0–P7 主链路已完成：Runtime、Humanoid、FSM、RootMotion、Jobs、Converter、bgfx demo。
- 测试基线：主构建 **195/195**；开启 `ANIM_ENABLE_ENTT=ON` 时 **196/196**。
- 性能优化：
  - `Transform` 使用 mecanim `xform` 3×float4（48B/16B 对齐）；
  - Blend 使用 SSE2 累加/归一化，单输入 Mixer/Layer 走 passthrough；
  - `computePalette` 使用世界 TRS 组合，避免额外 4x4 乘法；
  - `ThreadPoolJobScheduler` 支持跨角色并行。
- Release 基准（200 角色 × 64 骨 × 300 帧）：串行约 **1.9–2.0 ms/frame**，
  并行约 **0.35–0.47 ms/frame**（优化前 7.22 / 1.01）。
- 性能策略：xform float4 + SSE2 已完成，**不再以跨骨 SoA 为必做项**；
  单图内按链并行、曲线采样 profile 属于可选精确模式（性能优化），不阻塞发布。
- 当前范围与验收以 [17-功能范围与验收](17-功能范围与验收.md) 为准。
