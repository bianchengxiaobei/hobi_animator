# 05 · 人形肌肉空间与重定向

本层（L4）是整个项目最难、也最关键的模块。目标：**完整复刻 Unity humanoid 的肌肉空间（muscle space）管线**，使现有的 Unity `.anim` 人形动画能在**任意符合 humanoid 规范的骨架**上正确重定向（跨比例、跨模型）。

> 背景事实（来自实际 `.anim`，`Examples/Art/Humanoid Animations/Humanoid-Walk.anim`）：
> 人形动画**不存骨骼本地旋转**，而存 95 个归一化“肌肉”值 + `RootT/RootQ`（根位移/旋转）+ 手脚 IK 目标 `LeftFootT/Q`、`LeftHandT/Q`。
> 通用动画则存 `m_LocalRotation` + `path`（见 `SpiderBot-MoveUp.anim`）。
> Avatar 的骨名映射在 `.fbx.meta`（如 `DefaultHumanoid.fbx.meta`：`LeftUpLeg → LeftUpperLeg`）。

## 1. HumanBone（人形骨）

`include/anim/avatar/HumanBone.h`

必需 20 根（+ 可选）：
```cpp
enum class HumanBone : uint8_t {
    Hips, Spine, Chest, UpperChest /*可选*/, Neck, Head,
    LeftShoulder, LeftUpperArm, LeftLowerArm, LeftHand,
    RightShoulder, RightUpperArm, RightLowerArm, RightHand,
    LeftUpperLeg, LeftLowerLeg, LeftFoot, LeftToes,
    RightUpperLeg, RightLowerLeg, RightFoot, RightToes,
```

每根 `HumanBone` 在目标骨架中通过 `HumanoidAvatar::boneMap[humanBone]` 映射到 `Skeleton` 的骨骼索引（-1 表示缺省）。

## 2. 肌肉自由度（Muscle DOF）

Unity humanoid 共 **95 个肌肉**。每个肌肉 = “某骨骼的某根局部轴旋转”，值归一化到 `[-1,1]`，`0` 表示 T-Pose 静止。名称与轴映射是**固定规范**，与 `.anim` 中 `attribute` 名一一对应。经实测（`Humanoid-Walk.anim`）完整集合如下：

### 2.4 手指（可选）
每根手指三段 `1/2/3 Stretched`（X）+ `Spread`（Y），命名形如 `LeftHand.Thumb.1 Stretched`、`LeftHand.Index.Spread`。

> 实现上用一个**静态表** `MuscleTable[]`：`{MuscleId, HumanBone, Axis(X/Y/Z), Kind(Rotation/Twist/Stretch), Name}`。转换器与运行时共用（见 11）。完整 95 项按上表展开生成。

### 2.5 肌肉限制（limits）

每个肌肉 DOF 有一个角度范围。默认（无 Avatar 覆盖时）：
- 普通旋转（Front-Back/In-Out/Nod/Tilt/Turn/Close 等）：`±90°`。
- `Twist In-Out`：`±90°`（部分骨骼可到 `±180°`）。
- `Stretch`（LowerLeg/Forearm）：非对称，通常 `-30°..+90°` 一类的量级（以 Avatar/黄金数据标定）。
- 手指 `Stretched`：`-10°..+90°`；`Spread` 较小。
- **所有 limit 必须可由 Avatar 覆盖**；默认由离线 Unity 4.7 轴表/`.fbx.meta` 生成，Unity 2019 黄金数据校准为可选精确模式（见 13/17）。

## 3. 肌肉 → 骨骼本地旋转（核心公式）

Unity Mecanim 的肌肉不是三个独立的 `AngleAxis` 相乘，而是：

```
UVW = (DoF[2], DoF[1], DoF[0])       // Human2SkeletonPose 的倒序映射
u = tan( LimitUnproject(limitX, UVW.x) / 2 ) * signX
v = tan( LimitUnproject(limitY, UVW.y) / 2 ) * signY
r = tan( LimitUnproject(limitZ, UVW.z) / 2 ) * signZ

dq = normalize(Quat(w=1, x=u, y=v+u*r, z=r-u*v))
localRot[b] = restRot[b] * preRot[b] * dq * postRot[b]
```

- 上面 `Quat(w,x,y,z)` 是本库的 GLM 顺序；Unity 内部是 `(x,y,z,w)`。
- `UVW` 的顺序来自 `Bone2DoF[]`：`Bone2DoF[2]` 放进 `u`，`Bone2DoF[1]` 放进 `v`，
  `Bone2DoF[0]` 放进 `w`。因此不能用 `dqX*dqY*dqZ` 代替 `dq`。
- `preRot/postRot` 是 `skeleton::SetupAxes` 算出的**局部**值：
  `pre = R^-1 * parentQ^-1 * zeroQ * P`，
  `post = P^-1 * parentQ * R`。
  推导时 `R` 是目标骨 local rest，`parentQ` 是父骨 global rest，`boneQ = parentQ * R`；
  Unity 源公式为 `rawPre = parentQ^-1 * zeroQ * P`、
  `rawPost = boneQ^-1 * P`，本库保存的是 `R^-1 * rawPre` 和 `rawPost^-1`。
- `zeroQ / mainAxis / min / max / sign / forceAxis` 来自 Unity 4.7
  `mecanim/human` 的 `GetAxeInfo` 表；`P = quatMatrixToQuat(u,v,w)` 由
  T-Pose 的骨骼到子骨方向计算。
- 只有 1 个轴时 `ZYRoll` 退化为普通 `AngleAxis`；多轴时必须保留
  `ZYRoll2Quat` 的交叉项。
- 源实现对照：`Runtime/mecanim/human/human.cpp` 的
  `HumanSetupAxes` / `Human2SkeletonPose`（约 `:579` / `:1093`）、
  `Runtime/mecanim/skeleton/skeleton.cpp` 的 `SkeletonSetDoF` / `SetupAxes`
  （约 `:313` / `:439`），以及 `Runtime/mecanim/math/axes.h` 的
  `FromAxes`（约 `:115`）。

### 3.0 旧路径与离线 Unity 轴

- 没有 `uvw` 数据的旧 Avatar 仍走 `ΔqX*ΔqY*ΔqZ` 的兼容路径；它只用于旧测试/旧
  `anim_calibrate` 输出，不等价于 Unity。
- 有 `uvw` 数据的 Avatar 走上面的 `ZYRoll` 路径。`tools/unity_humanoid_axes.py`
  可以直接从 `.fbx.meta` + 本地 Unity 4.7 源码生成 `uvw/preRot/postRot/limitsOverride`，
  不需要 Unity Editor。

### 3.1 为什么需要 T-Pose

肌肉值定义为**相对 T-Pose 的偏移**（0 = T-Pose）。因此目标骨架必须能构造 T-Pose（或等价的“肌肉空间静止姿态”）。`HumanoidAvatar` 保存：
```cpp
struct HumanoidAvatar {
    int boneMap[(int)HumanBone::Count];
    Transform restLocal[/*每骨*/];     // 目标骨架 T-Pose（局部）
    Quat preRot[...], postRot[...];    // 由 T-Pose 推导/标定
    std::array<MuscleLimit, kMuscleCount> limits;
    std::array<HumanoidAxisBinding,3> uvw[/* HumanBone */];
    bool hasUvw[/* HumanBone */];      // true 时走 ZYRoll
    HumanoidBoneAxes axes[/* HumanBone */]; // Unity Axes 快照（可选）
    float hipsHeight;                  // 用于根运动跨比例缩放
    float armTwist, foreArmTwist;      // Unity HumanDescription，默认 0.5
    float upperLegTwist, legTwist;     // 供 applyHumanoidTwist 使用
};
```

## 4. 根（RootT / RootQ）与根运动

- `RootT.x/y/z`：Hips 在 root space 的完整 local 位移；`RootQ.x/y/z/w`：Hips 在 root space 的完整 local 旋转。
- 它们是 Hips 的 root transform，不是相对 T-Pose/rest 的 delta。
- Unity 的 `HumanPose.m_RootX` 由 `HumanComputeRootXform`（`human.cpp` 约 1310 行）计算为 **mass-center root**；
  `RetargetTo` 用该 root 调整 Hips local。本库默认采用 **Hips-root**：直接把
  `RootT/RootQ` **覆盖**到 Hips 的 local TRS；设置
  `HumanoidRootMode::MassCenter` 时改为按默认骨质量与肢体朝向计算 mass-center root，
  朝向与 Unity `HumanComputeOrientation` 一致，乘以 setup/rest 朝向的共轭；
  Hips 调整在世界空间完成后再转回父 local（支持 Armature 父级）；
  存在独立 root 骨时把 root 写到目标 mass-root，Hips 再按父链局部化；
  手脚 goal 也与该 mass-center root 保持一致。
- root space 由 T-Pose 的朝向定义（Unity 约定：面朝 +Z、上为 +Y，脚在原点附近）。
- 跨比例重定向：按 `humanScale = target.hipsHeight / source.hipsHeight` 缩放 `RootT`；本库使用单一 `humanScale`，不单独处理高度轴。
- 根运动提取（04 的 `extractRootMotion`）在应用 `RootT/RootQ` 之后读取 Hips 的世界/根空间变化。

## 5. 手脚 IK 目标

`.anim` 中还有：
- `LeftFootT/Q`、`RightFootT/Q`、`LeftHandT/Q`、`RightHandT/Q`。
- 它们是 IK goal 的位置/旋转（body 相对空间）。仅当对应 IK 开关打开时生效（`ApplyFootIK`/`ApplyAnimatorIK`，原项目见 `ClipState.cs:69-90`）。
- 本库：`applyHumanoidGoals()` 可按显式权重把 goal 桥接到源码式两骨几何求解，
  并在超出链长时按 Unity `Skeleton2BoneAdjustLength` 做最大 5% 拉伸；也可由
  引擎消费原始 goal。另有 `applyHumanoidTwist()` 和 `applyHumanoidLookAt()` 桥接。
  source avatar 带 Axes 时两骨 DoF 走 `ToAxes/FromAxes`，twist 走
  `SkeletonAlign`，goal rotation 后走 `HumanFixEndDoF`；跨比例缩放由
  `RetargetFrom`/`RetargetTo` 的 `humanScale` 处理。
  权重遵循 `FullBodySolve`：
  raw goal 传给 `Skeleton2BoneIK`，只有拉伸距离使用
  `lerp(当前末端, goal, WeightT)`。

## 6. 重定向流水线（Route A）

```
HumanoidClip (肌肉空间, 与骨架无关)
   │ sample(t): 得到 95 muscles + RootT/Q + IK goals
   ▼
MuscleSpace::toLocal(muscles, avatar, out Pose):
   for each HumanBone with any muscle:
       localRot = restRot * preRot * ΔqX * ΔqY * ΔqZ * postRot   (公式 §3)
   apply RootT/RootQ to Hips (完整 root TRS; translate 缩放 by humanScale)
   (可选) 应用 IK goals
   ▼
Pose (目标骨架本地 TRS)  ──▶ 上层的混合/输出
```

关键点：**源 Clip 不含任何骨骼信息**，所以同一 Clip 可直接用于任意目标骨架——这正是 Route A 相对“按骨名复制本地旋转”的价值。

## 8. 验证策略

1. **单骨标定**：构造只动一根骨（如 Spine X）的测试 Clip，在 Unity 与 C++ 各采样 `t`，对比该骨 local rotation。
2. **全骨逐帧**：`Humanoid-Walk.anim` 在 0..length 均匀取 N 点，dump 每骨 local TRS（见 13），逐骨比对，容差 `<1e-4`。
3. **跨骨架**：用第二个不同比例的人形模型播放同一 Clip，验证相对动作一致（无源骨架也能正确）；当前用同拓扑缩放，真实第二模型用于视觉/retarget 回归，不要求逐值对比。
4. **根运动**：对比 Hips 世界轨迹与 delta。

> 全骨逐帧 Unity 数值对拍属于可选精确模式；默认发布验收以功能测试、Unity 4.7 离线 fixtures 和视觉验收为主（见 [17](17-功能范围与验收.md)）。
>
> 若某骨对不上，优先怀疑 `preRot/postRot` 与 limit；用“单骨—单轴”最小用例二分定位。

### 11.1 P4.1 标定工具链（Editor / 离线两条路）

由于 Unity 的 `Animator`/`Avatar`/`HumanPoseHandler` 是闭源黑盒，本库提供两条链路：

**A. 有 Unity Editor：Editor dump → C++ 反解**

1. **Unity 侧**：`Assets/AnimancerCppCalibration/Editor/HumanoidGoldenDumper.cs`
   - 菜单 `Tools/AnimancerCpp/Dump Humanoid Muscle Golden`。
   - 用 `HumanPoseHandler.SetHumanPose` 每次只设置一个 muscle 为
     `-1/-0.5/+0.5/+1`，记录该 muscle 对应骨骼的 `localRotation`；
     同时记录零肌肉 T-Pose 作为 `rest`。
   - 同时用 `HumanTrait.GetMuscleDefaultMin/Max` 记录 Unity 默认 limits。
   - 输出 `AnimancerCpp/golden/HumanoidGolden.json`。
   - 采样时使用与 C++ 相同的模型/Avatar，避免 T-Pose 不一致。
2. **C++ 侧**：`include/anim/avatar/HumanoidCalibration.h`
   - 对单轴样本计算
     `D = rest^-1 * localRotation = pre * Rot(canonicalAxis, θ) * pre^-1`。
   - `D` 的轴给出 `pre * canonicalAxis`；同骨 X/Y/Z 三轴还原 `pre`，
     `post = pre^-1`；`θ / muscle` 得到 max，`-θ / -muscle` 得到 min。
   - 仅提供 1/2 个轴时用最短弧/叉积补全；最后用原始样本回代，超过
     `toleranceDegrees`（默认 0.1°）即失败。回代角度使用相对四元数的
     `2*atan2(|xyz|, |w|)`，避免 `acos(dot)` 在接近单位四元数时的精度损失。
   - 反解结果写回 `HumanoidAvatar::preRot/postRot/limits`；未被采样的
     muscle 使用 Unity `defaultLimits` 覆盖静态表默认值：
     `applyHumanoidCalibration()`。
3. **转换 CLI**：
   ```bash
   anim_calibrate --golden golden/HumanoidGolden.json \
                  --out avatar.json --tolerance 0.1
   ```
   输出兼容转换器的 `avatar.json`，额外包含 `preRot`、`postRot`、
   逐 muscle `limitsOverride` 和 `calibrationMaxErrorDegrees`。
   `AvatarLoader` 会解析 `preRot/postRot`；`AvatarBuilder` 把它们和
   `limitsOverride` 一起应用到 `HumanoidAvatar`。`anim_converter` 自身

### 11.3 已知差异与当前边界

以下差异和简化是当前已接受方案；范围见 [17-功能范围与验收](17-功能范围与验收.md)，
不再阻塞发布。

1. **Unity 2019 黄金数据（可选精确验证）**：`<0.05°` 全骨逐帧对拍不属于发布门槛；
   当前由 Unity 4.7 离线 fixtures + 功能测试覆盖回归，有环境时再执行 11.2 的 dump。
2. **Root：Hips-root 默认 + 可选 mass-center**：Unity `HumanComputeRootXform`
   （`human.cpp` 约 1310 行）把 `HumanPose.m_RootX` 算成 mass-center root，
   `RetargetTo` 用它调整 Hips local。本库默认 Hips-root；可选
   `HumanoidRootMode::MassCenter` 已按默认骨质量、缺失骨质量迁移和肢体朝向实现；
   朝向按 `HumanComputeOrientation` 相对 setup/rest 朝向计算，Hips 调整按世界空间
   再局部化到父级，存在独立 root 骨时写入目标 mass-root；
   手脚 goal 同步使用 mass-center root 提取/应用。
3. **`kEulerXYZ`（已补精确路径）**：Unity `axes.h` 的 `ToAxes/FromAxes`
   对 `kEulerXYZ` 使用 `quatQuatToEuler` / `quatEulerToQuat`；C++ 已按
   `Runtime/Math/Simd/quaternion.h` 公式实现并接入 type 3。当前资源仍主要使用
   ZYRoll，type 3 的视觉资产回归保留为可选。
4. **`FullBodySolve`（已接受桥接）**：Unity 的完整求解在 `human.cpp` 约 2128 行；
   本库保留两骨 IK、twist 分配和 look-at 分段桥接，不逐行移植完整迭代顺序。
   该桥接是当前方案，只有视觉验收出现明显头/眼/胸姿态问题时才重新评估。
5. **第二个人形模型（视觉/retarget 回归）**：当前用离线缩放的同拓扑第二骨架验证；
   真实第二个人形 FBX 只用于视觉/retarget 回归，不要求与 Unity 逐值对比。
6. **标定与 limits 的默认行为**：新 `HumanoidAvatar` 的 `preRot/postRot` 默认
   identity，`MuscleEntry::defaultLimit` 只是兜底；正式资源应使用离线
   `unity_humanoid_axes.py` 或 Editor dump + `anim_calibrate` 生成非单位标定和
   limits。这是数据准备要求，不是 Unity 2019 对拍阻塞。
